# 设计笔记

这份文档记的是**为什么这么做**，以及**踩过哪些坑**。

README 讲怎么用，这里讲实现上的取舍 —— 尤其是那些"看起来可以那么写、但实际会出问题"的地方。踩过的坑都标了 ⚠️，省得重犯。

---

## 为什么是无障碍，而不是 ADB / Shizuku

一开始走的是 ADB 路线（靠 Shizuku 拿 shell 身份），后来换成了无障碍。原因是：

| | ADB / Shizuku | **无障碍** |
|---|---|---|
| 额外安装 | 要装 Shizuku | **不用** |
| **重启后** | ❌ **要重新用无线调试启动** | ✅ **自动恢复** |
| 截图 | ✅ 干净，能截安全窗口 | ⚠️ 有限流，安全窗口截不到 |
| 多指手势 | ❌ `input` 只支持单指 | ✅ **天然支持** |
| 中文输入 | ❌ 要装 ADBKeyboard 或走剪贴板 | ✅ **直接灌文本** |

**决定性的一条是"重启后自动恢复"。** Shizuku 在无 root 手机上每次重启都要重新用无线调试启动一次，日常使用太折腾。无障碍授权一次就常驻。

代价是截不到安全窗口（银行密码键盘那种 `FLAG_SECURE` 页面），以及对一个每步 3-8 秒的 AI 循环来说无所谓的截图限流。

### 定位策略：UI 树为主，截图辅助

这是本项目最关键的架构选择。

**纯视觉方案**（只看截图点像素）有个绕不开的问题：**模型算的坐标会偏**。Roubao 的 issue 里坐标偏移是第二高频问题，作者甚至承认"所有横屏设备都无法使用"。

**读 UI 控件树能直接从系统拿到元素的精确 bounds** —— 坐标不需要模型猜，也就不会偏。两者分工明确：

```
截图        →  理解语义（这一屏是什么界面、该做什么）
UI 控件树   →  精确定位（点哪个元素）
```

## 几个关键实现细节

### 1. UI 树要压缩，不能原样丢给模型

无障碍给的原始节点树又深又吵，还有大量无意义的容器节点。直接丢给模型既浪费 token 又干扰判断。`UiNode.kt` 的过滤规则：

- 只留可交互（可点/可滚/可编辑）或有文字/描述的
- 面积小于 24×24 的丢掉（装饰线、占位符）
- 完全在屏幕外的丢掉（列表滚动后的残留）
- 同样的位置 + 文字只留一个（去重）

压缩后渲染成这样，模型从里面选编号：

```
[1] Button "登录" @(540,2175) [可点]
[2] EditText "手机号" @(540,1200) [可点,可输入]
[3] TextView "忘记密码?" @(880,2300) [可点]
```

### 2. 按编号点击比按坐标准

节点对象**不能跨帧缓存** —— 界面一变就失效。所以每次操作都重新解析一遍树，再定位到对应编号。

点击时先试节点级 `ACTION_CLICK`（最准），点不动才退回坐标手势（有些自定义控件不响应节点点击）。

### 3. `ACTION_SET_TEXT` 是无障碍最大的红利

```kotlin
node.performAction(AccessibilityNodeInfo.ACTION_SET_TEXT, bundle)
```

**直接设字符串，任意 Unicode 都行，不需要任何额外依赖。**

对比 ADB 方案：`input text` 只支持 ASCII，中文要么装 ADBKeyboard、要么走剪贴板 + keyevent 279，两种都很别扭。

优先级：当前焦点节点 → 树里第一个可编辑节点 → 提示用户先点输入框。

### 4. 截图要重试

无障碍截图会撞上平台限流（`ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT`，API 30+）。代码里做了 3 次重试 + 递增等待。**这不是优化，是必需的容错。**

另外 `takeScreenshot` 返回的是硬件位图，要 `copy(ARGB_8888)` 转成软件位图，否则后续 `getPixel` 或跨线程使用会出问题。

### 5. 单指手势：一个统一模型，七个动作

这是手势层的核心设计（`GestureSpec.kt`）。

**所有单指动作都是同一个三段式的参数变体**：

```
按下 ──┬── 移动 ──┬── 停顿 ── 松手
       │          │
       │      滑动有停顿，甩动没有
       └── 拖拽在这里加长按
```

| 动作 | 按下后停顿 | 移动 | 松手前停顿 |
|---|---|---|---|
| 单击 | — | 短 | — |
| 长按 | — | — | —（按住时间长） |
| 双击 | — | 短 ×2 | —（两次单击） |
| 滑动 | — | 有 | **有** |
| 甩动 | — | 有（快） | **无** |
| 拖拽 | **有**（超长按阈值） | 有 | — |

#### 为什么"松手前停顿"能区分滑动和甩动

惯性滑动靠的是**松手瞬间的速度**。系统根据手指抬起前的移动速度决定是否继续滚一段。

- 划完**停顿一下**再松 → 停顿期间速度归零 → 不触发惯性 → **滑动**
- 划完**立刻松** → 保持速度 → 继续滚一段 → **甩动**

一个参数就把两者分开了，不需要两套实现。

实现上停顿是"在路径终点再补一个重合点"：

```kotlin
if (spec.restBeforeUpMs > 0) {
    path.lineTo(x2, y2)   // 终点重合点 → 手指停住 → 速度归零
}
val stroke = StrokeDescription(
    path,
    spec.holdBeforeMoveMs,                 // 按下后等这么久才开始移动
    spec.moveMs + spec.restBeforeUpMs,     // 移动 + 停顿
)
```

#### 为什么拖拽头部要长按

**系统的拖拽判定看的是"按下后多久开始移动"** —— 必须超过长按阈值，系统才进入拖拽模式。

之前的实现只是把移动过程拉长到 800ms、按下后立刻开始动，那会被系统当成"慢速滑动"，移动图标、调滑块这类会失败。

现在用 `ViewConfiguration.getLongPressTimeout()` 拿**设备真实阈值**（不同 ROM 可能不一样），再加 100ms 余量：

```kotlin
fun drag(longPressTimeout: Long, moveMs: Long = 500) = GestureSpec(
    holdBeforeMoveMs = longPressTimeout + 100,
    moveMs = moveMs,
)
```

#### 滚动：节点级优先

`smartScroll` 先找面积最大的可滚动节点走 `ACTION_SCROLL_FORWARD`（不需要坐标、不会滚过头），失败才退回**甩动**手势（回退用甩动而不是滑动 —— 滚动列表期待的就是惯性效果）。

### 6. 双指暂时搁置

双指捏合/张开在代码里能跑（`dispatchGesture` 支持多路径），但按计划先只把单指做扎实。双指旋转、双指点击暂缓。

## AI 决策循环

```
   截图 + 控件树 ──→ 模型 ──→ 解析动作 ──→ 执行 ──→ 等一会儿 ──┐
        ↑                                                      │
        └──────────────────────────────────────────────────────┘
```

### 提示词里的两条硬规则

**定位优先用编号，不是坐标。** 发给模型的除了截图，还有一份控件树编号列表（形如 `[3] Button "登录" @(540,2175) [可点]`）。模型从"猜一个像素坐标"变成"选一个数字"。只有列表里找不到目标时，才退回让它给 x/y。

**只输出一个 JSON 对象。** 但提示词拦不住模型 —— 它照样会加 markdown 围栏、加解释文字、编造动作名。所以 `ActionParser` 做了完整的防御：剥围栏 → 提取第一个**配平**的花括号块（要正确处理字符串里的花括号）→ 解析 → 动作名过白名单 → 坐标夹紧 → 缺参数就拒绝执行。任何一步失败都不抛异常，而是把原因**回灌给模型让它重出**。

### 三个防护

| 防护 | 做法 | 为什么需要 |
|---|---|---|
| 画面没变 | 截图 MD5 连续 3 步相同 → 下轮提示里点破 | 光靠步数上限拦不住"30 步全点在同一个没反应的位置" |
| 动作重复 | 动作签名连续 3 次相同 → 强制换动作 | 画面哈希会被时钟/加载圈干扰，需要第二道 |
| 成本 | **历史不带图**，只有当前轮发截图 | 30 步每步一张 1080×2400，token 会翻好几倍 |

另有一条：「自己在前台就让位」—— 无障碍截图抓的是整块物理屏，纸盒自己在前台时截到的就是纸盒的界面，模型会开始点我们自己的按钮。所以循环开始前检查前台包名，是我们就先按 Home。

### 不烧真 Key 的验证方法

`tools/mock_llm.py` 是一个假的 OpenAI 兼容服务，按剧本返回动作：

```bash
python3 tools/mock_llm.py
# 模拟器里接口地址填 http://10.0.2.2:8765（这是模拟器访问宿主机的固定地址）
```

剧本里故意混了 markdown 围栏、编造的动作名、越界坐标，用来验证防御性解析真的在工作。

## 悬浮控制面板

AI 跑起来之后主界面会退到后台，这时用户看不到进度、也点不到停止。所以任务开始时起一个悬浮窗：

```
┌─────────────────────────────┐
│ ┌─────────────────────────┐ │
│ │ 第 3 / 30 步             │ │  ← 左上角状态卡
│ │ 正在：点击「网络和互联网」 │ │
│ │ 下一步：打开 WiFi 设置    │ │  ← 黄色，模型对下一步的预判
│ └─────────────────────────┘ │
│                             │
│        （透明，看得到底下的应用）
│                             │
│           ╭─────────╮       │
│           │  急停   │       │   ← 底部居中，红色
│           ╰─────────╯       │
└─────────────────────────────┘
```

### 为什么是"悬浮窗"而不是"透明的 Activity"

需求原话是"做一个透明的 Activity 浮在应用上层"。**这在 Android 上做不到**：Activity 一旦启动，被它盖住的应用就退到后台、不再渲染了 —— 透明背景也救不了，你看到的会是壁纸而不是那个应用。

能真正"浮在别的应用之上"的只有两条路：

| | 悬浮窗 `TYPE_APPLICATION_OVERLAY` | 画中画 |
|---|---|---|
| 全屏透明 | ✅ | ❌ 做不到 |
| 左上角 + 底部居中布局 | ✅ | ❌ 窗口小、只能在角落 |
| 需要用户授权 | 要 | 不要 |

按要的界面只有悬浮窗放得下，所以用 `Service + WindowManager`。**画面效果和需求描述完全一致**，区别只是它在系统眼里叫"窗口"不叫"Activity"。

### 两个独立窗口，不是一个全屏窗口

一个全屏窗口会把整块屏幕变成可触摸区域，AI 注入的点击会打在它身上。拆成两个 `WRAP_CONTENT` 小窗口之后：

- **状态卡**：`FLAG_NOT_TOUCHABLE`，永不吃点击
- **急停钮**：可触摸，但只有它那一小块

其余区域完全是空的，用户还能同时正常用手机。

### 截图前必须藏起来

无障碍截图抓的是整块物理屏。不藏的话：

1. 悬浮窗会出现在图里，模型会把"急停按钮"当成界面元素去点
2. 注入的点击若落在按钮上，会被它吃掉 —— 甚至点到"急停"把自己的任务停掉

所以每一步是：`隐藏 → 等 100ms → 截图 → 显示`，注入同理。

### 三个踩过的坑（都记在这里免得重犯）

**1. 用 `INVISIBLE` 不是 `GONE`。**
`GONE` 会让 view 退出测量布局，而悬浮窗的尺寸是在布局里定下来的 —— 结果是 GONE 过一次之后窗口尺寸退化，状态卡缩成一条只剩内边距的灰色竖条，文字全没了。`INVISIBLE` 保留占位和尺寸，只是不绘制，正好是我们要的。

这个做法参考了肉包（Roubao）的 `OverlayService`：它用的就是 `INVISIBLE`，而且"隐藏 100ms → 截图 → 显示"这段时序也和我们一致。

**2. `WRAP_CONTENT` 的窗口不会自己重新测量。**
文字变长后 view 会 `requestLayout`，但窗口尺寸不会跟着变。所以状态卡用了**固定尺寸**（232×96dp），顺带还有个好处：面板不会随文字长短忽大忽小。

**3. 加 `FLAG_KEEP_SCREEN_ON`**（也是从肉包学的）。
任务跑到一半屏幕自动熄灭的话，无障碍截图会直接失败。加了这个标志，悬浮窗还在屏幕就不睡。

### 急停

三个入口，都能用：

| 入口 | 特点 |
|---|---|
| 悬浮窗上的红色按钮 | 最顺手 |
| 通知栏里的「急停」 | 悬浮窗正好被藏着时的退路 |
| 主界面的停止按钮 | AI 跑完回到前台后还能用 |

按下之后**不是立刻砍断**，而是在两个检查点生效：每步开始时、以及"动作已决定但还没注入"时。第二个检查点最关键 —— 它能把响应窗口从"一步"缩短到"一次模型调用"，而且保证正在发起的那次注入不会被半路打断。

### 权限

悬浮窗是**特殊权限**，代码申请不了，必须跳系统设置手动开（`Settings.ACTION_MANAGE_OVERLAY_PERMISSION`）。各家 ROM 入口名字不同，ColorOS 还可能要先解开"受限制的设置"。

没开也能用 —— 任务照常跑，只是看不到面板也停不下来，所以主界面在缺权限时会明确提示一次。

## 构建环境的坑（中文路径 / 网络）

`services.gradle.org` 会 307 跳转到 `downloads.gradle.org`，后者国内基本连不上，报 `Connection refused`。**这不是配置错误，是网络问题。**

工程里已经换成腾讯云镜像：

```properties
distributionUrl=https\\://mirrors.cloud.tencent.com/gradle/gradle-8.9-bin.zip
validateDistributionUrl=false
```

> `validateDistributionUrl=false` 是必须的 —— Gradle 默认会去官方源校验，换成镜像后校验必然失败。

**改完还报同样的错**，说明缓存了失败记录：

```bash
rm -rf ~/.gradle/wrapper/dists/gradle-8.9-bin
```

然后 `File → Sync Project with Gradle Files`。

依赖包如果也慢，可以换阿里云镜像 —— 改 `settings.gradle.kts` 里的 `dependencyResolutionManagement`，把阿里云的三个仓库加到前面。`gradle.properties` 里也已经配好了超时和重试参数。

## 上下文：无限继承，且必须缓存友好

### 为什么不裁剪

早期实现里有一段"只保留最近 12 轮"的裁剪。删掉了，原因有两个，第二个才是关键。

**原因一：裁剪会打断缓存前缀。**

服务端的上下文缓存是按**最长公共前缀**复用的。一裁剪，对话的开头就变了，下一次请求从第一条消息起就对不上 —— 后面所有内容全部按未命中计价。**为了省 token 去裁剪，结果反而更贵。**

**原因二（更严重）：历史和实际发出去的内容根本不是一份东西。**

原来的写法是这样的：

```kotlin
// 发出去的是带控件树的长文本
val userText = AgentPrompt.stepMessage(step, ..., uiTree = tree)
llm.chat(system, history, userText, shot)

// 但事后只往历史里补了一句执行结果
history.add(ChatTurn(ASSISTANT, result.text))
history.add(ChatTurn(USER, "第 N 步执行结果：已执行"))
```

也就是说：**带控件树的那条 user 消息从来没有进过历史**。下一次请求的 messages 序列，从 system 之后的**第一条**就和上一次不同。

缓存命中率不是"低"，是**恒等于 0**。而且 trim 的存在让问题更难看出来 —— 看起来像是"裁剪导致的"，其实不裁剪也命中不了。

### 怎么改的

让 `history` 就是**实际发出去的那份 messages**：

```kotlin
// 1. 先把本轮 user 消息原样追加进 history
history.add(ChatTurn(ChatTurn.USER, userText))

// 2. 再发 —— 图片挂在最后一条 user 消息上，其余一律纯文本
val result = llm.chat(system, history, shot)

// 3. 模型的原始输出也原样追加
history.add(ChatTurn(ChatTurn.ASSISTANT, result.text))
```

关键是不再单独发"执行结果"那种消息 —— 它被拼进**下一条** user 消息里：

```
[system][user1][assistant1][user2][assistant2]...
           └─ 严格追加，前缀永不变动
```

这样从第 2 步开始，system + 前面所有轮次全部命中缓存。

### 图片怎么办

只有**最后一条** user 消息带图片。历史轮次的图不带。

这是个取舍：图片留在历史里能让前缀 100% 逐字节一致，但代价是每次请求都要重传之前所有截图 —— 30 步下来是几十 MB 的上传量。

所以接受"在最新那张图那里断一次"：**断点之后只有当前这一轮的图**，断点之前（system + 全部文本历史）依然命中。

### 怎么验证

`tools/mock_llm.py` 会把每次请求的消息序列和上一次比对，打印前缀复用了几条：

```
=== 第 2 次请求 ===
  消息数    : 4  上次 2 条
  前缀复用  : 2 / 2 条   ✅ 前缀完整保留

=== 第 3 次请求 ===
  消息数    : 6  上次 4 条
  前缀复用  : 4 / 4 条   ✅ 前缀完整保留
```

真机跑任务时，日志末尾也会有一行命中率：

```
上下文缓存：命中 36000 / 未命中 2800（命中率 93%）
```

**这行如果是 0%，先查 history——一定是有人往里面塞了和实际发送不一致的东西。**

### 那上下文无限涨怎么办

不裁剪就得有兜底。用服务端返回的**真实** `prompt_tokens` 判断，比本地估算准：

- 超过 `CONTEXT_WARN_TOKENS`（默认 100k）→ 日志告警
- 超过 `CONTEXT_STOP_TOKENS`（默认 120k）→ 停下任务并说明原因

这两个常量在 `Agent.kt` 里，按所用模型的窗口大小调整。

> 选择"停下"而不是"偷偷丢掉最老的几轮"：丢上下文会让模型突然忘记前面做过什么，产出莫名其妙的行为，而用户完全不知道为什么。明确停下并说明，比悄悄降智好。
